# 2. Downscale 설계 결정 배경

Updated: `2026-02-15`

## 요약
- Redis는 클러스터 멤버를 `nodeID/masterID` 기준으로 관리합니다.
- Kubernetes StatefulSet은 Pod를 `ordinal` 기준으로 축소합니다.
- `cluster-allow-replica-migration=yes` + 다배수 follower 환경에서는 Pod 이름과 실제 샤드 소속이 섞일 수 있습니다.
- 이 상태에서 downscale하면 Redis 정리 대상과 StatefulSet 삭제 대상이 어긋나 의도하지 않은 노드 삭제 또는 unjoined Pod(좀비) 잔존이 발생할 수 있습니다.
- 예를 들어 shard 정리 시 `follower-4`, `follower-9`, `follower-13`의 nodeID를 먼저 제거해도, STS는 high ordinal부터 축소하므로 `follower-4`, `follower-9`이 깡통 상태로 남을 수 있습니다.

따라서 현재는 운영 안정성을 우선해 `cluster-allow-replica-migration=no`와 `spec.clusterSize` 단일 스케일 모델을 채택했습니다.

## 문제 상황
Redis Cluster downscale(특히 leader 감소) 과정에서 다음 위험을 확인했습니다.

- Pod 이름 기준 그룹(`leader-4`, `follower-4/9/13`)
- 실제 Redis 복제 관계(`masterID/nodeID`)

운영 중에는 이 두 정보가 항상 일치하지 않습니다.

개선 전 문제 재현 전제는 다음과 같습니다.
1. `cluster-allow-replica-migration=yes`
2. leader 대비 follower 다배수 운영(예: leaders=5, followers=10)

이 전제에서는 샤드 구성원이 고정되지 않아, downscale 시 의도하지 않은 node 삭제 또는 unjoined Pod(좀비) 잔존이 발생할 수 있습니다.

## 개선 전 코드 동작 요약

### 1) follower 초기 연결
- 파일: `internal/k8sutils/cluster/exec_cluster.go`
- 함수: `ExecuteRedisReplicationCommand`
- 규칙: `followerOrdinal % leaderCount`로 초기 leader를 선택해 `--cluster-slave` 수행

중요 포인트:
- 위 규칙은 초기 배치 규칙입니다.
- 이후 failover/migration/수동 `CLUSTER REPLICATE`가 발생하면 실제 소속은 달라질 수 있습니다.

### 2) downscale 정리
- 파일: `internal/controller/rediscluster_controller.go`
- 흐름:
1. overflow leader pod에서 `GetEffectiveMasterNodeIDByPod`로 source master 결정
2. source master 직속 follower nodeID 삭제
3. source master reshard
4. source master del-node
5. rebalance

중요 포인트:
- 기준은 Pod 이름이 아니라 `masterID/nodeID`입니다.
- 초기 소속 그래프가 유지될 때는 문제가 작지만, 그룹이 섞이면 원하지 않은 Pod의 nodeID가 삭제 대상이 될 수 있습니다.
- 예: 초기 `{leader-4, follower-4/9/13}`였더라도 `leader-4` Pod의 `masterID`가 `leader-1` shard를 가리키게 되면, downscale 시 `leader-1` 쪽 replica 정리에 포함될 수 있습니다.

### 3) StatefulSet 축소
- StatefulSet은 높은 ordinal부터 삭제합니다.
- 예: follower 10->8이면 `follower-9`, `follower-8` 삭제

중요 포인트:
- 클러스터에서 제거한 nodeID와 STS가 실제 삭제하는 Pod ordinal이 다를 수 있습니다.
- 그 결과 low ordinal Pod가 살아남지만 클러스터 밖인 unjoined 상태가 될 수 있습니다.

## 핵심 원인
문제는 두 축의 불일치입니다.

1. 클러스터 정리 축: `nodeID/masterID`
2. Kubernetes 축소 축: `pod ordinal`

이 두 축이 어긋나면,
- 삭제 범위가 의도보다 커지거나
- 의도한 Pod는 남고 멤버십만 빠진 좀비 상태가 생깁니다.

## 검토한 선택지

### 선택지 A: migration 허용 + 다배수 follower 유지
장점:
- 토폴로지 유연성
- 상황에 따라 replica 재배치 가능

단점:
- downscale 예측 가능성 하락
- nodeID 삭제와 ordinal 삭제 불일치 리스크 증가
- 회귀 테스트/정합화 로직 비용 증가

### 선택지 B: migration 비활성 + 스케일 모델 단순화 (채택)
채택 정책:
1. `cluster-allow-replica-migration no`
2. `spec.clusterSize` 단일 스케일 소스 사용
   (leader/follower replica 분리 입력 미사용)

장점:
- downscale 경로 단순화
- 예측 가능성 향상
- 운영 리스크 감소

### 선택지 C: migration 비활성 + 다배수 follower 유지
핵심 리스크:
- migration을 꺼도, nodeID 정리 순서와 STS ordinal 축소 순서가 다르면 unjoined Pod가 남을 수 있습니다.

예:
- 가정: leader `5 -> 4`, follower `15 -> 12`(리더당 follower 3개), 삭제 대상 shard의 follower가 `follower-4`, `follower-9`, `follower-13`
- 클러스터 정리 단계에서 `follower-4`, `follower-9`, `follower-13`의 nodeID가 멤버십에서 먼저 제거됨(del-node)
- 이후 StatefulSet 축소는 규칙상 high ordinal Pod부터 내려서 `follower-14`, `follower-13`, `follower-12`를 삭제함
- 이때 `follower-13`은 실제로 삭제되지만, `follower-4`와 `follower-9` Pod는 ordinal이 낮아 살아남을 수 있음
- 결과적으로 `follower-4`, `follower-9`은 Pod는 Running인데 클러스터에는 없는 unjoined(깡통/좀비) 상태가 될 수 있음

## 최종 결론
이번 결정은 기능 축소가 목적이 아니라,
**downscale 시 데이터/토폴로지 안정성을 우선 확보하기 위한 보수적 설계 선택**입니다.

즉, "할 수 있는 기능"보다 "안전하게 운영 가능한 경로"를 우선했습니다.

## 향후 다배수 follower 재도입 조건
다음이 준비되면 재도입 가능합니다.

1. `followerPerLeader` 기반 스펙 모델 도입
2. follower 배치 규칙 deterministic 보장
3. 목표 master 불일치 시 `CLUSTER REPLICATE` 정합화 로직 추가
4. nodeID 정리 순서와 STS ordinal 축소 순서 일치화
5. failover/downscale E2E 회귀 테스트 확보
